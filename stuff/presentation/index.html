Legal research in India is mostly manual. Advocates, especially in the district courts, law students and legal-aid clinics find candidate sections in the bare act, read the commentary for the ingredients, search judgments for precedent, and then read for hours. [click] Three things make it harder now: since July 2024 there are two criminal codes in use, AI tools that promise speed invent citations, and precedent is split, because the new code has almost no case law yet. The first of these is the core problem.

A section number means nothing without its code, and the offence date decides the code.

The Bharatiya Nyaya Sanhita replaced the Indian Penal Code on 1 July 2024, and almost every offence got a new number. Offences committed before that date are still tried under the IPC, so for years every lawyer works with both. [click] 302 is murder in the IPC; in the BNS it is hurting religious feelings. [click] 303 was murder by a life-convict; in the BNS it is theft. [click] And 420, the best-known cheating section, does not exist in the BNS at all. [click] So a citation that is right in one code is a different crime, or nothing, in the other. That is exactly where AI tools go wrong.

Problem statement

Build a research assistant for Indian criminal law that identifies applicable sections and precedents across the IPC→BNS transition, and never presents a non-existent citation.

The second problem: language models invent citations. Asked what BNS 303 covers, the model confidently described a bomb-threat offence. [click] BNS 303 is theft. [click] When we let it answer from memory on 15 development cases, 20 of its 68 citations named sections that do not exist in the BNS, mostly old IPC numbers. [click] This is not only small models: a Stanford and Yale study published in 2025 found the leading commercial legal AI research tools hallucinating on 17 to 33 percent of queries. [click] So the problem statement: build a research assistant for Indian criminal law that finds the applicable sections and precedents across the transition, and never presents a non-existent citation. The gap

No system we found combines date-based code routing, graph-verified citations, an IPC→BNS precedent bridge, counter-arguments and outcome statistics.

On the research side: retrieval-augmented generation grounds a model’s answer in retrieved text, but nothing in it checks that a citation exists. LeSICiN identifies statutes with a graph model, but it is supervised and IPC-only. IL-TUR is the Indian legal benchmark. Magesh and colleagues, at Stanford and Yale, measured hallucination in commercial tools. BGE-M3 is a strong general embedder. On the tool side: Indian Kanoon is a free search engine, and Manupatra and SCC Online are subscription databases; they return real documents but do not map facts to sections. jhana.ai and NyayAssist are AI research assistants that link and check citations, so verification alone is not new. [click] The gap is the combination, which no system we found offers: choosing the code by offence date, graph-verified citations, bridging new BNS charges to old IPC precedent, counter-arguments and outcome statistics. That is what we built.

03 · Our solution · how we do it

Four steps: route, retrieve, verify, ground.

01RouteThe offence date picks the code: IPC or BNS. A fixed rule, no AI.
02RetrieveFind candidate sections from statute text and from similar past judgments.
03Propose & verifyThe AI proposes sections; the citation graph confirms each one exists.
04Ground & argueTest each section on the facts, find precedents, draft counter-arguments.

The AI proposes. The graph decides what is real.

Our approach has four steps. [click] Route: the offence date picks the code, IPC or BNS, with a fixed rule; no AI is involved. [click] Retrieve: find candidate sections, both from statute text and from similar past judgments. [click] Propose and verify: the AI proposes sections, and a citation graph built from the statutes confirms that each one exists in that code. [click] Ground and argue: test each section against the facts, find precedents, and draft counter-arguments. The principle behind it: the AI proposes, the graph decides what is real. 05 · Multi-agent pipeline

Six agents, one shared state.

Code
Language model
Graph lookup
Each agent reads and writes only its own fields of the state, so every step can be checked on its own.
The pipeline is a set of agents built with LangGraph, all reading and writing one shared, typed state: the facts, the date, the code, the candidates, what was verified or rejected, the precedents and the defences. [click] The statute identifier, a language model, proposes sections from the facts and the candidates. The verifier checks each one in the citation graph; if any is rejected, the case goes back to the identifier with the reason, at most twice. [click] The applicability judge, a language model guided by fixed legal rules, tests whether each real section fits the facts. [click] Then two agents run in parallel: the precedent matcher walks the citation graph, including the bridge from BNS to IPC, and the outcome analyst counts how appeals were decided with plain SQL. [click] Finally the defence drafter writes counter-arguments, and a final check verifies everything it cites. Let me take the agents one at a time, starting with verification.

Existing is not the same as applying, so agent 2b, the applicability judge, tests every verified section against the facts. Here is a different saved case: a stabbing after a parking quarrel. [click] The judge must quote the facts for each ingredient: a kitchen knife, a stab to the abdomen, a perforated intestine, an injury dangerous to life. [click] Culpable homicide is a real section, but it is doubted, because it requires a death and the facts report grievous hurt. [click] Agent four then drafts three counter-arguments, and a final check confirms each one targets a charge, quotes the facts word for word, and cites only precedents it was given. The technology stack, layer by layer, with the reason for each choice. The knowledge layer: ChromaDB holds the vectors, persistent and filterable by metadata; NetworkX holds the citation graph, which gives an exact existence check; SQLite holds the outcome counts. The intelligence layer: BGE-M3 for embeddings, chosen by a measured comparison against a legal-domain model, and qwen 3.5, an open-weight 4-billion-parameter model served through Ollama, whose answers are constrained to a JSON schema. Orchestration is LangGraph rather than one big prompt, because we need the retry edge, parallel agents and a state we can check after every step.
